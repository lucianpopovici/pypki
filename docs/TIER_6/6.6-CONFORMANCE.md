# Tier 6.6 — Conformance batteries

## Why this matters

PyPKI's own tests confirm what we intended. Third-party conformance batteries
confirm what the RFCs actually require. There's always a gap. Conformance
testing is the cheapest way to find the gap before an operator does.

Most of these batteries are publicly published test data + a runner harness.
Little new code; mostly plumbing.

## Batteries

| Battery                                          | Covers                                    | Effort      |
| ------------------------------------------------ | ----------------------------------------- | ----------- |
| NIST PKITS                                       | RFC 5280 path validation                  | Low         |
| Let's Encrypt Pebble compliance                  | ACME (RFC 8555 + extensions)              | Low         |
| RFC 5280 corner-case suite (hand-rolled)         | basicConstraints, name constraints, AKI/SKI, critical-extension handling | Medium |
| BetterTLS                                        | name constraints (web PKI variant)        | Low         |
| OpenSSL `crl-test` and `cert-test` corpora       | DER edge cases                            | Low         |
| draft-ietf-lamps test vectors for ML-DSA in X.509 | ML-DSA signature verification             | Low (once published) |

## NIST PKITS

The Public Key Interoperability Test Suite is the canonical RFC 5280 path
validation battery. The corpus is publicly distributed, no licence issues.

- Download data into `conformance/pkits/data/` (committed; <5 MB).
- `runner.py` walks each test case (a target cert, trust anchors, CRLs, and
  an expected validation outcome) and feeds it through PyPKI's path
  validator.
- Compare the result to `expected.json`.
- Any divergence is a finding: either PyPKI is wrong, or the expected
  value documents an intentional deviation (with rationale).

Caveat: PKITS tests some behaviours we explicitly do not implement (e.g.,
specific policy mappings). Those tests are marked `"expected": "skipped"`
in `expected.json` with a comment pointing at the rationale.

## Pebble compliance

Let's Encrypt's Pebble has a compliance test mode that exercises an ACME
server against the spec. Point it at PyPKI's ACME endpoint, run, collect
results. Pebble runs in docker, no host-system dep.

Operations exercised: account creation, EAB binding, order, finalize,
challenges (http-01, dns-01), revocation, key rotation, error responses
(`urn:ietf:params:acme:error:*`).

## RFC 5280 corner cases (hand-rolled)

PKITS doesn't cover everything. Worth hand-authoring cases for:

- `basicConstraints.pathLenConstraint = 0` on intermediate; verify
  three-level chains reject.
- `nameConstraints` with `directoryName`, `iPAddress`, `dNSName`, `URI`,
  `rfc822Name`; including IPv6 ranges, IDN domains, and edge masks.
- AKI keyIdentifier vs AKI issuer+serial; mismatched cases.
- SKI present / absent / wrong.
- Critical extension we don't understand: must reject.
- `notBefore` > `notAfter`: must reject at parse.
- Validity periods crossing year-2038 and year-9999 boundaries.
- Negative integer serial (RFC violation): must reject.
- Zero-length serial: must reject.
- Algorithm parameter encoding for RSASSA-PSS (RFC 4055 §3.1).

Each case lives in `conformance/rfc5280_corners/cases/<name>/` with a
short `README.md` explaining the case and `expected.txt` documenting the
outcome. The runner is a thin walker over the directory.

## BetterTLS

Covers name-constraints behaviour as deployed by web PKI. Useful even though
we're not a web-PKI CA, because the test cases are real-world subtle.
Runner is in Go; we shell out from `runner.sh`.

## ML-DSA vectors

Once `draft-ietf-lamps-x509-mldsa` (or equivalent) publishes test vectors,
import them and verify signature checking against the known-good cases. Hold
until the document stabilizes.

## Conventions

- **No conformance test silently passes when skipped.** Skipped tests must
  print why and contribute to the summary as `SKIPPED`, not `PASSED`.
- **Results checked into the repo.** `results.md` per battery, updated on
  every successful run. Reviewers see drift in PRs.
- **One-shot fix policy.** If a conformance test reveals PyPKI doesn't
  implement something we claim, fix forward — don't downgrade the
  expectation.
- **Battery-specific dependencies live in the battery's directory.** PKITS
  needs nothing. Pebble needs docker. BetterTLS needs Go. Document in each
  battery's `README.md`.

## CI integration

- **Per-PR** — PKITS + RFC 5280 corners run on every PR. Fast (~30 s for
  PKITS, ~10 s for corners) and high-signal.
- **Nightly** — full suite including Pebble, BetterTLS, ML-DSA vectors.
- **Pre-release tag** — full suite is a required gate.

## Findings → fixes

A conformance failure is one of:

1. **PyPKI bug** — fix the bug, add a regression to `test_pki_server.py`,
   re-run the battery to confirm. CHANGELOG `### Fixed` or `### Security`.
2. **Intentional deviation** — document in the battery's `expected.json` /
   `expected.txt` with rationale and a link to `docs/COMPATIBILITY.md`.
   Updating expected outcomes silently is forbidden.
3. **Battery bug** — rare, but report upstream and document with a TODO.

## Per-change checklist (RFC 5280 path-validation code)

- [ ] PKITS still green
- [ ] RFC 5280 corner cases still green
- [ ] If a new check is added, a corner-case file for it added
- [ ] CHANGELOG entry

## Success criteria

Tier 6.6 is "done" when:

1. PKITS runs in CI with results.md committed.
2. Every PKITS deviation has a documented rationale.
3. Pebble compliance is green in nightly CI.
4. The RFC 5280 corner-case suite has at least 30 cases covering the bullet
   list above.
5. BetterTLS runs nightly and results are tracked.
6. ML-DSA vectors imported and verified (once published).
