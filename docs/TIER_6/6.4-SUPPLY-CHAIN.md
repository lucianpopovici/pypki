# Tier 6.4 — Supply chain

## Why this matters

PyPKI is a CA. The supply chain of the binary an operator runs is part of
the trust chain of every certificate it issues. We need to be able to
answer, for any released artifact, "what's in it, who built it, can I
verify it bit-for-bit?"

This work is independent of the other Tier 6 streams — run it in parallel.

## Deliverables

1. **CycloneDX SBOM** generated at build time, attached to every GitHub
   release, committed alongside the release tag.
2. **Signed release artifacts** — `pypki-main.zip` and any container images
   signed with Sigstore / cosign. Public key (or Fulcio identity) published
   in the README.
3. **Pinned dependencies with hashes** — `requirements.txt` uses
   `--require-hashes` format. Dev deps in `requirements-dev.txt` likewise.
4. **Reproducible builds** — same git tag, on a fresh container, must
   produce a byte-identical `pypki-main.zip`. CI verifies this on every
   release tag.
5. **Vulnerability scanning** — `pip-audit` (or `osv-scanner`) in CI,
   gating on high/critical.
6. **Container image hardening** — distroless or chiseled base, non-root
   user, read-only root filesystem, no shell.

## Tooling (all dev-only)

| Tool             | Purpose                                       | Where invoked       |
| ---------------- | --------------------------------------------- | ------------------- |
| `cyclonedx-py`   | Generate SBOM from `requirements.txt`         | Release workflow    |
| `pip-audit`      | Scan deps against PyPI advisory DB / OSV      | Per-PR CI           |
| `cosign`         | Sign and verify release artifacts             | Release workflow    |
| `diffoscope`     | Reproducible-build diff on failure            | Release workflow    |
| `syft` (option)  | Container SBOM if we publish images          | Release workflow    |

None of these are imported by PyPKI runtime code. They go in
`requirements-dev.txt` and are installed in CI only.

## Reproducible build recipe

Reproducibility requires:

- **Fixed timestamps**: `SOURCE_DATE_EPOCH` set to the tagged commit's
  timestamp. Zip entries written with that mtime.
- **Stable file ordering**: directory listings sorted before archiving.
- **Stable permissions**: explicit `0644` for files, `0755` for dirs in
  the archive.
- **No bytecode**: don't ship `.pyc` files; let the consumer compile.
- **Pinned Python and OS**: build runs on a fixed image tag (e.g.,
  `python:3.12.7-slim-bookworm@sha256:<digest>`).

Build script: `scripts/build_release.sh`. Two invocations on a fresh
container with the same tag must produce identical SHA-256.

Verification job: `repro-check` in `.github/workflows/release.yml`. Runs the
build twice in clean environments, compares outputs, fails if they differ.
`diffoscope` produces the human-readable diff on failure.

## Dependency posture

- `requirements.txt` — runtime deps only. Currently just `cryptography`,
  `requests`, and the `libpam0g` ctypes wrapper (no pip install). Each
  pinned to an exact version and SHA-256 hash via `pip-compile --generate-hashes`.
- `requirements-dev.txt` — test, fuzz, build, lint, audit tools. Same hash
  pinning.
- **Renovate / Dependabot**: enabled, but PRs are reviewed by hand. We
  don't auto-merge dep bumps for a CA.
- **License audit**: every dep's license recorded in
  `docs/LICENSES.md`. New deps require explicit license entry in the PR.

## Container image (if/when we publish one)

```dockerfile
# Build stage
FROM python:3.12.7-slim-bookworm@sha256:... AS build
COPY requirements.txt .
RUN pip install --require-hashes -r requirements.txt --target /pkgs

# Runtime stage — chiseled / distroless
FROM gcr.io/distroless/python3-debian12@sha256:...
COPY --from=build /pkgs /app/pkgs
COPY pypki/ /app/pypki/
USER 65532:65532
WORKDIR /app
ENV PYTHONPATH=/app/pkgs
ENTRYPOINT ["python", "-m", "pypki"]
```

- Non-root UID/GID (65532, distroless convention).
- Read-only root filesystem (`docker run --read-only` works).
- No shell in the final image. No package manager. No CA bundle (PyPKI
  brings its own).
- Image tag = git tag. Digest pinned in deployment manifests.

## CI gates

A PR cannot merge if:

- `pip-audit` reports a HIGH or CRITICAL.
- `requirements.txt` has unpinned versions or missing hashes.
- A new dependency was added without a `docs/LICENSES.md` entry.

A release tag cannot publish if:

- SBOM generation fails.
- Reproducibility check shows any diff.
- Cosign signing step fails.

## Per-change checklist (dependency change)

- [ ] `requirements*.txt` regenerated with `pip-compile --generate-hashes`
- [ ] `docs/LICENSES.md` updated
- [ ] `pip-audit` clean
- [ ] SBOM regenerated locally to confirm it parses
- [ ] CHANGELOG `### Security` or `### Changed`

## Per-change checklist (release)

- [ ] Tag matches `vX.Y.Z` semver
- [ ] `scripts/build_release.sh` produces `pypki-main.zip`
- [ ] SHA-256 recorded in release notes
- [ ] CycloneDX SBOM attached to release
- [ ] `cosign sign-blob` produces signature, attached to release
- [ ] Reproducibility verification green
- [ ] Container image (if published) signed and digest pinned

## Verification by consumers

The README needs a "Verifying a release" section:

```bash
# Download artifacts
curl -LO https://github.com/lucianpopovici/pypki/releases/download/v1.0.0/pypki-main.zip
curl -LO https://github.com/lucianpopovici/pypki/releases/download/v1.0.0/pypki-main.zip.sig
curl -LO https://github.com/lucianpopovici/pypki/releases/download/v1.0.0/pypki-main.zip.pem

# Verify with cosign (keyless / Fulcio)
cosign verify-blob \
  --certificate pypki-main.zip.pem \
  --signature pypki-main.zip.sig \
  --certificate-identity-regexp '^https://github.com/lucianpopovici/pypki/' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  pypki-main.zip
```

## Success criteria

Tier 6.4 is "done" when:

1. Latest release has SBOM, cosign signature, and reproducibility proof.
2. CI gates above are active and have rejected at least one PR (proof they
   work).
3. README "Verifying a release" section walks a new operator through
   verification successfully.
4. All runtime deps are hash-pinned in `requirements.txt`.
5. Container image (if any) is distroless / non-root / read-only-FS
   compatible.
