# Tier 6.5 — Chaos & failure injection

## Why this matters

PyPKI's operational invariants assume things complete or fail cleanly. The
real world doesn't oblige. The audit log invariant — "every issued
certificate is recorded" — is the one whose failure is hardest to detect and
hardest to forgive. Chaos testing is how we prove the code survives the
ugly cases: process kills mid-sign, DB failover, disk full, HSM yanked,
clock jumps.

## Invariants to defend

These are non-negotiable. The chaos suite exists to prove each holds under
every failure mode below.

| # | Invariant                                                                       |
| - | ------------------------------------------------------------------------------- |
| 1 | No certificate exists on disk or in a chain that isn't recorded in `audit_log` |
| 2 | No two certificates share a serial number, ever                                |
| 3 | `cRLNumber` is strictly monotonic across restarts and DB failovers              |
| 4 | A revoked certificate stays revoked across DB failover and replica promotion    |
| 5 | An ACME order's state survives a server restart                                 |
| 6 | An OCSP response signed at time T reflects the revocation state at time T      |
| 7 | An audit-log entry is durable before the cert is returned to the client         |
| 8 | The advisory lock on serial allocation is never held by a dead process          |

## Failure modes to inject

| # | Failure                                                          | Affects invariants  |
| - | ---------------------------------------------------------------- | ------------------- |
| F1 | `SIGKILL` to PyPKI between sign and audit-log commit            | 1, 7                |
| F2 | `SIGKILL` to PyPKI between audit-log commit and HTTP response   | 1, 2                |
| F3 | DB process killed mid-transaction                                | 1, 2, 7             |
| F4 | HSM session severed during `C_Sign`                              | 1, 7                |
| F5 | Disk full during CRL write                                       | 3                   |
| F6 | Disk full during audit-log write                                 | 1, 7                |
| F7 | Webhook receiver hangs indefinitely                              | 1 (don't block), 7  |
| F8 | Webhook receiver returns 500 repeatedly                          | 1, 7                |
| F9 | Postgres primary failover during issuance                        | 2, 3, 4, 8          |
| F10 | Postgres replica lag at OCSP query time                         | 4, 6                |
| F11 | Network partition between PyPKI and OCSP responder              | 6                   |
| F12 | Clock jump forward (NTP sync) during issuance                   | 6                   |
| F13 | Clock jump backward during issuance                              | 3 (cRLNumber)       |
| F14 | Two PyPKI instances issuing concurrently against same DB        | 2, 3, 8             |

Each scenario file is self-contained:

```python
def setup(): ...        # bring PyPKI + dependencies up in a known state
def inject(): ...       # trigger the failure
def assertions(): ...   # run every applicable invariant check
def teardown(): ...
```

## Tooling

- **Process control**: `os.kill`, `subprocess`, `docker-compose stop/start`.
  No `toxiproxy`, no `pumba` — both are new deps. Network failures simulated
  with `iptables` rules inside the test container, or `tc netem`.
- **Postgres failover**: `docker-compose` with primary + replica, scripted
  promotion. No external orchestrator.
- **Clock manipulation**: `libfaketime` (LD_PRELOAD-injected into the
  process under test, not into PyPKI's dependency closure).
- **Disk full**: bind-mount a small tmpfs at the audit-log / CRL output
  path, fill it, run.

All test infrastructure stays under `chaos/` and never imports into PyPKI
itself.

## How invariants are checked

Each invariant has a checker in `chaos/invariants/`. Examples:

**`audit_log_complete.py`**: enumerate every cert in `certificates` table,
every cert serial in any saved chain, every cert on disk under
`ca-dir/issued/`; assert each has an `audit_log` row with `event_type
IN ('issue', 'reissue')` and a matching serial.

**`no_duplicate_serials.py`**: `SELECT serial, COUNT(*) FROM certificates
GROUP BY serial HAVING COUNT(*) > 1` returns zero rows.

**`crl_number_monotonic.py`**: parse every CRL ever issued (stored in
`ca-dir/crl/history/`), assert `cRLNumber` strictly increases.

**`revocation_persists.py`**: revoke cert, force failover, re-query —
revocation must persist with same `revoked_at` and `reason`.

Each invariant runs after every chaos scenario. A failure is a release
blocker.

## Conventions

- **No real production data ever.** Chaos runs against ephemeral test CAs.
- **State is wiped between scenarios.** Cross-scenario contamination has
  caused false negatives before.
- **Postgres scenarios require Postgres.** Skipped (clearly) when not
  available, never silently passed.
- **Findings get fixed before merge.** Chaos failures are not "known
  issues" — they are bugs in the durability of the system.
- **Document the OS-level requirement** (libfaketime, iptables, tmpfs) in
  `chaos/README.md`. Skip with a clear message on environments where it's
  unavailable rather than hanging or false-passing.

## CI integration

- **Per-PR** — chaos suite does NOT run. Too slow, too flaky on shared
  runners.
- **Nightly** — full suite. Failures file issues and block the next
  release.
- **Pre-release tag** — full suite is a required gate.

Invocation: `./run_tests.sh --chaos`.

## Findings → fixes

A chaos finding means an invariant broke. Workflow:

1. Capture the failure: process logs, DB state, file-system snapshot.
2. Reduce: minimize the sequence of operations needed to reproduce.
3. Add a permanent regression to `test_pki_server.py` under a new class
   `TestTier6Chaos<area>` that exercises the recovery path
   deterministically (not via real signal injection).
4. Fix the bug.
5. CHANGELOG `### Fixed` or `### Security`.
6. Keep the chaos scenario in the suite forever as a guard.

## Per-change checklist (durability-sensitive change)

Anything that changes how state is committed — DB writes, file-system
writes, lock acquisition, signal handling — needs:

- [ ] Relevant chaos scenarios re-run locally
- [ ] If a new failure mode is plausible, new scenario added
- [ ] Invariants still pass

## Success criteria

Tier 6.5 is "done" when:

1. Every failure F1–F14 has a scenario file.
2. Every invariant 1–8 has a checker.
3. Nightly runs are green for two consecutive weeks.
4. At least one real bug has been found and fixed via chaos (if not,
   the suite probably isn't pressing hard enough — make it harder).
5. `docs/THREAT_MODEL.md` references the chaos suite for durability
   guarantees (cross-link to 6.3).
