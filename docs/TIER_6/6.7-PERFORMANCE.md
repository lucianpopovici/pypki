# Tier 6.7 — Performance baseline

## Why this matters

Operators sizing a PyPKI deployment ask three questions: how fast can it
issue, how fast can it answer OCSP, how big does the DB get. Today the
answer is "we don't know." Tier 7 (adoption) needs numbers.

Tier 6.7 also acts as a regression gate: a 20%+ slowdown on any documented
metric blocks release without explanation.

## Metrics

### Issuance throughput

Certs/second sustained, per CA key type, single PyPKI instance, SQLite
and Postgres backends, with and without HSM.

| CA key type   | Backend  | HSM | Target |
| ------------- | -------- | --- | ------ |
| RSA-2048      | SQLite   | No  | Bench  |
| RSA-2048      | SQLite   | Yes | Bench  |
| RSA-2048      | Postgres | No  | Bench  |
| RSA-4096      | SQLite   | No  | Bench  |
| ECDSA P-256   | SQLite   | No  | Bench  |
| ECDSA P-384   | SQLite   | No  | Bench  |
| ECDSA P-521   | SQLite   | No  | Bench  |
| Ed25519       | SQLite   | No  | Bench  |
| Ed448         | SQLite   | No  | Bench  |
| ML-DSA-44     | SQLite   | No  | Bench  |
| ML-DSA-65     | SQLite   | No  | Bench  |
| ML-DSA-87     | SQLite   | No  | Bench  |

"Target" is "Bench" — we record numbers, we don't promise a SLA. (SLA
language belongs in deployment runbooks, per-deployment.)

### OCSP throughput

Responses/second, single OCSP responder, SQLite.

- Live signing (per-request fresh response)
- Pre-generated (file-system lookup of pre-signed responses)
- Mixed (some serials hit pre-gen, some fall through to live)

### CRL generation time

Time to generate and sign a CRL, varying revoked-cert count:

- 1k revoked
- 10k revoked
- 100k revoked
- 1M revoked

Plot the curve. Document where the cliff is. If there's a cliff at 1M,
that's a feature-gap to note for Tier 7.

### ACME order completion

p50 / p95 / p99 latency, end-to-end from `newOrder` to issued cert:

- http-01 with a local responder
- dns-01 with the Pi-hole hook

### CMP transaction latency

p50 / p95 for `ir`, `cr`, `kur`. Includes signature protection, response
generation, audit-log write.

### Storage growth

Bytes per issued cert in `certificates` table, plus per audit-log row.
Multiply by issuance rate to estimate disk growth for capacity planning.

### Concurrent issuance scaling

Single PyPKI process, threaded handlers, 1 / 4 / 16 / 64 concurrent
clients. Where does throughput plateau? Where does latency cliff?

## Harness

```
bench/
├── README.md                # how to run, what hardware to use
├── _harness.py              # shared timing + metric collection
├── issuance.py              # parameterized over key type + backend
├── ocsp.py
├── crl_gen.py
├── acme.py
├── cmp.py
├── storage.py
└── results/
    ├── 2026-Q2-issuance.md
    ├── 2026-Q2-ocsp.md
    └── ...
```

- Drives PyPKI via its public APIs (REST, ACME, CMP, OCSP) — no internal
  shortcuts. Numbers must reflect real client behaviour.
- Re-uses Prometheus instrumentation already in `pki_server.py`,
  `ocsp_server.py`, `acme_server.py`. Each bench dumps the relevant metrics
  at the end of the run.
- Single run = warm-up + measure. Warm-up not counted.
- Results format is markdown: hardware spec, OS, Python version, PyPKI
  commit, command line, table of numbers, optional flame graph link.

## Reference hardware

Numbers need context to be meaningful. Document one reference profile:

- CPU: 8-core x86_64, baseline 3.0 GHz (e.g., a typical mid-tier VM)
- RAM: 16 GB
- Disk: NVMe SSD, ext4
- Python 3.12.7
- SQLite or Postgres 16 (call out which)

Re-runs on different hardware get a separate `results/` file, never
overwrite the reference numbers.

## Output

Final deliverable: `docs/PERFORMANCE.md`. Structure:

1. Reference hardware
2. How to reproduce (single shell invocation per metric)
3. Tables of numbers, one per metric class
4. Brief commentary on bottlenecks (e.g., "RSA-4096 is signing-bound, not
   DB-bound, as expected")
5. Capacity planning examples ("at 10 certs/sec sustained on RSA-2048, DB
   grows ~X MB/day")

The doc must be reproducible by anyone with the source tree. If a number
in the doc can't be reproduced, it doesn't go in the doc.

## Conventions

- **No microbenchmarks of internal functions.** Bench against public APIs.
  Internals get refactored; user-visible perf doesn't.
- **No averaged-only numbers.** Always p50/p95/p99 for latency, sustained
  rate over ≥ 60 s for throughput. Means hide tail behaviour.
- **Document what you turned off.** If a bench disables audit logging or
  webhooks to isolate a number, say so in the result file.
- **One commit per re-run.** Results are timestamped and tagged with the
  PyPKI commit they were taken from. Comparing across versions requires
  identical methodology.
- **No marketing in numbers.** Don't quote "1000 certs/sec" if it's a
  best-case spike. Quote the sustained number you can defend.

## CI integration

- **Per-PR** — does NOT run. Bench results are noisy on shared CI runners.
- **Pre-release tag** — run the full suite on a dedicated benchmark
  machine (or a fixed reference VM image), compare to last release's
  numbers.
- **Regression gate** — > 20% slowdown on any documented metric blocks
  release. The gate is informational only until a release has set the
  baseline; once baseline exists, enforced.

## Per-change checklist (perf-sensitive change)

Anything touching the hot path — signing, DB writes, CRL generation, OCSP —
needs:

- [ ] Relevant bench re-run on the reference hardware
- [ ] Numbers compared to last release; any regression > 20% explained in
      the PR description
- [ ] `docs/PERFORMANCE.md` updated if the published numbers change

## Success criteria

Tier 6.7 is "done" when:

1. `docs/PERFORMANCE.md` exists, with numbers reproducible from the source
   tree.
2. Every metric class above has at least one result file.
3. Numbers are documented for a reference hardware profile.
4. Pre-release bench is wired into the release workflow and has run at
   least once.
5. Tier 7 messaging can cite real numbers, not adjectives.
