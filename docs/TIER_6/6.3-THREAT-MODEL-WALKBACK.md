# Tier 6.3 — Threat model walkback

## Why this matters

`docs/THREAT_MODEL.md` was written during Tier 4. Since then PyPKI has grown
new privilege boundaries, new outbound network paths, and new key-handling
surfaces. The threat model has not been re-tabletop'd against them. That's a
gap, and the longer it stays open the more likely a future change lands on
an unmodeled assumption.

## Surfaces added since the original threat model

Each of these introduces at least one new attacker, asset, or trust
boundary:

1. **RA approval workflow** (`pki_server.py`, `web_ui.py`, `cmp_server.py`,
   `acme_server.py`, `est_server.py`) — multi-actor approval, new privilege
   tier between "requester" and "CA operator."
2. **ACME EAB** (`acme_server.py`) — per-account HMAC binding; key
   distribution and compromise scenarios.
3. **Per-account ACME rate limiting** (`acme_server.py`) — denial-of-service
   for legitimate accounts via key enumeration.
4. **Cross-signing** (`pki_server.py`, `web_ui.py`) — chain confusion,
   misissuance via swapped sub-CA CSRs.
5. **Paired ML-DSA + classical issuance** (`pki_server.py`) — RFC 9763
   `RelatedCertificate` linkage; downgrade attacks; rollback to classical
   only.
6. **Lifecycle webhooks** (`hooks.py`, `pki_server.py`) — outbound HTTP,
   SSRF risk, replay if the receiver is compromised.
7. **HSM / PKCS#11** (`hsm_backend.py`) — PIN handling, slot enumeration,
   key extraction posture.
8. **Postgres dual-backend** (`db.py`, `migrations.py`) — TLS to DB, replica
   lag, advisory-lock failure modes, credential storage.
9. **Pre-generated OCSP responses** (`ocsp_server.py`, `pypki_admin.py`) —
   stale-response window, file-system trust, signature reuse.
10. **SCEP one-time challenges** (`scep_server.py`, `web_ui.py`) — replay,
    enumeration, challenge brute-force.
11. **CT pre-cert flow** (`pki_server.py`) — SCT injection by hostile log,
    log misbehaviour, log unavailability.
12. **Ed25519/Ed448/ECDSA/ML-DSA CA keys** — key handling and serialization
    for non-RSA algorithms.

## Process

Tabletop each surface in turn. One session per cluster:

| Session | Clusters                                          |
| ------- | ------------------------------------------------- |
| A       | RA workflow, ACME EAB, ACME per-account limiting  |
| B       | Cross-signing, paired issuance, CT pre-cert       |
| C       | Webhooks, HSM, Postgres                           |
| D       | Pre-generated OCSP, SCEP OTC, non-RSA key types   |

For each surface, fill in:

```markdown
### <surface>

**Trust boundary**: <who's on each side>
**Asset**: <what we're protecting>
**Attackers**:
  - <attacker 1>: <capabilities>
  - <attacker 2>: <capabilities>
**Threats**:
  - <STRIDE category>: <specific scenario>
**Existing mitigations**:
  - <code reference>: <what it does>
**Residual risk**: <what we accept and why>
**Tests**: <test_pki_server.py class / method that proves the mitigation>
```

If "Tests" is empty for a real mitigation, that's a gap. Add a test.

If "Existing mitigations" doesn't actually cover a stated threat, that's a
finding. Open a fix.

## Specific things to check

These are the lurking assumptions worth poking at:

- **RA workflow**: does the audit log distinguish "approved by X" from
  "issued by Y"? Is the approver identity bound into the issued cert
  somehow, or only into the log?
- **EAB key storage**: are EAB keys stored hashed or in plaintext? If
  plaintext, why?
- **Cross-signing**: what stops an operator from cross-signing an attacker
  CSR with a misleading subject? Is there an out-of-band confirmation step
  documented in the runbook?
- **Paired issuance**: if the classical cert is revoked, does the ML-DSA
  cert auto-revoke? Should it?
- **Webhooks**: is the destination URL allow-listed? Does the request bear
  an HMAC the receiver can verify? Replay window?
- **HSM**: PIN provided how? Environment variable, file, prompt? Is it ever
  logged? What happens on HSM disconnect during signing?
- **Postgres**: TLS required? Connection-pool credential cycling? What if
  the replica has stale revocation state when OCSP queries it?
- **Pre-gen OCSP**: how long is the response valid? What happens if a cert
  is revoked between pre-gen runs?
- **SCEP OTC**: challenge length? Storage? TTL? Rate limit on attempts?

## Conventions

- **Update `docs/THREAT_MODEL.md` in place.** Don't fork. The doc is the
  source of truth.
- **Cite code with file:line.** When mitigations reference code, link to
  the exact line so the doc rots loudly when the code moves.
- **No vendor names in threats.** "An attacker with API access" is
  portable; "An attacker who has popped the Slack channel" is not.
- **Residual risk gets accepted explicitly.** Don't pretend a risk is
  mitigated when it isn't. Write it down as accepted, by whom, with a
  rationale.

## Per-change checklist (any change touching a privilege boundary)

- [ ] Reviewed against the relevant `docs/THREAT_MODEL.md` section
- [ ] If new threat surface, added a new section
- [ ] If new mitigation, added a test that proves it
- [ ] If residual risk is new, called out in PR description
- [ ] CHANGELOG `### Security` entry if the risk posture changed

## Success criteria

Tier 6.3 is "done" when:

1. Every surface in the list above has a section in `docs/THREAT_MODEL.md`.
2. Every "Existing mitigations" entry has a test reference.
3. Every "Residual risk" entry is explicitly acknowledged with rationale.
4. Any new gap discovered during walkback has either been fixed or
   explicitly accepted in writing.
5. The doc's "Last reviewed" header matches the current minor release.
