# Tier 6.2 — Interop matrix

## Why this matters

The README compliance table claims a long list of RFCs. Unit tests prove
PyPKI's own client/server pair agrees with itself. Interop testing proves
PyPKI agrees with the implementations operators will actually point at it.

Every protocol must round-trip against at least one independent reference
client. Failures are the single most actionable signal we have for "is the
implementation right."

## Layout

```
interop/
├── README.md                # how to run, what each test does
├── INTEROP_MATRIX.md        # current pass/fail/manual status — keep updated
├── scep/
│   ├── docker-compose.yml   # PyPKI + sscep container
│   ├── run.sh
│   └── expected.md
├── acme/
│   ├── docker-compose.yml   # PyPKI + Pebble's Boulder-light test setup
│   ├── certbot/run.sh
│   ├── acme-sh/run.sh
│   ├── lego/run.sh
│   └── caddy/run.sh
├── est/
├── cmp/
├── ocsp/
├── tsa/
├── crl/
├── smime/
├── mldsa/
└── pkcs12/
```

Each protocol directory holds:

- `docker-compose.yml` — PyPKI + one or more reference clients
- `run.sh` — bootstraps PyPKI (clean state), runs the client through the
  required ops, asserts success
- `expected.md` — what success looks like, including known-quirk notes
  (e.g., "openssl cmp ≤ 3.2.0 omits `algorithms` from genm response —
  ignored")

## Conventions

- **No new runtime deps.** All interop tests live in containers; reference
  clients install in those containers, not in PyPKI's environment.
- **Each `run.sh` is idempotent.** Tear down and rebuild on every invocation.
  State leaks between runs cause non-determinism we don't want.
- **One trust anchor per test.** PyPKI starts fresh, mints its CA, runs the
  exchange, verifies. We don't share root certificates across interop tests.
- **Wire captures on failure.** Failed runs dump the relevant request /
  response bodies to `interop/<protocol>/_failures/<ts>/` for triage. DER and
  PEM where applicable.
- **No external network.** Pebble runs locally for ACME. DNS challenges use
  the `dns_pihole.sh` hook against a local Unbound. We never reach out to
  Let's Encrypt staging from CI.

## Manual interop (Outlook, Thunderbird, Cisco IOS, Windows NDES)

These can't be automated cheaply. Document them in
`interop/MANUAL_RUNBOOK.md`:

- Setup steps (test VMs, lab gear)
- Expected behaviour and screenshots
- Last-tested-on date and PyPKI commit
- Known gaps

Re-run at least once per minor release.

## Per-change checklist

Any time we touch a wire-protocol module:

- [ ] Relevant interop test still passes locally (`bash interop/<proto>/run.sh`)
- [ ] If behaviour changed in a way clients might care about, update
      `INTEROP_MATRIX.md`
- [ ] If a new feature has wire impact (e.g., new CMP message type), add a
      reference-client invocation that exercises it
- [ ] Wire-capture diffs against the previous baseline reviewed by hand

## CI integration

- **Per-PR** — full required matrix runs. Caching makes this ~5 minutes.
- **Pre-release tag** — required + best-effort, plus the manual runbook is
  re-walked.

## Findings → fixes

Every interop bug gets:

1. Captured wire-level: request and response DER + PEM dump.
2. A regression test in `test_pki_server.py` that constructs the exact bytes
   the reference client sent and asserts PyPKI's parser handles them.
3. A fix in the protocol module.
4. A note in `INTEROP_MATRIX.md` if a client-side workaround is now also
   tolerated.

## Success criteria

Tier 6.2 is "done" when:

1. Every "Required" row in the matrix is green in CI.
2. `INTEROP_MATRIX.md` exists and reflects current state.
3. Manual runbook has been walked at least once on current code.
4. Every protocol has at least one wire-capture fixture in the corpus that
   came from a reference client (fed back to Tier 6.1 as fuzz seeds).
