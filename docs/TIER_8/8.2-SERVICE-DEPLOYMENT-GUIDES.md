# Tier 8.2 — Per-service deployment guides

## Why this matters

`docs/DEPLOYMENT/` today is organized by topology (homelab, k8s,
offline-root, VPN, IoT). That's useful but not the question most operators
ask first.

Most operators ask "how do I deploy PyPKI's `<ACME / SCEP / OCSP / EST /
CMP / TSA / S-MIME / Web UI>` server?" first, then pick a topology. The
existing docs invert that ordering — service usage is scattered across
topology docs, sometimes only briefly mentioned.

8.2 adds a service-first layer that points into the topology docs at the
right places. Topology docs stay as the canonical install reference;
service guides answer "now that PyPKI is installed, how do I run this
specific service?"

## Services in scope

Every protocol server PyPKI exposes, plus the management surfaces:

| Service          | Module                            | Existing topology docs that touch it       |
| ---------------- | --------------------------------- | ------------------------------------------ |
| ACME             | `acme_server.py`                  | `k8s-cert-manager.md`, `pihole-acme-dns01.md` |
| SCEP             | `scep_server.py`                  | (loosely in `iot-est.md`)                  |
| EST              | `est_server.py`                   | `iot-est.md`                               |
| CMP              | `cmp_server.py`                   | `vpn-strongswan-cmp.md`                    |
| OCSP             | `ocsp_server.py`                  | `homelab.md` (briefly)                     |
| CRL distribution | `pki_server.py` (CRL endpoints)   | `homelab.md` (briefly)                     |
| TSA              | `tsa_server.py`                   | —                                          |
| S/MIME           | `smime_server.py`                 | —                                          |
| Web UI + REST    | `web_ui.py`, `pki_server.py`      | `homelab.md`                               |

TSA and S/MIME have no existing deployment doc at all today. Those guides
are the highest-value adds.

    ├── pypki-acme.service
    ├── pypki-ocsp.service

`docs/HOWTO/README.md` is a single-screen index: one row per service,
columns are "what it does," "when to use it," "RFC," "guide link."

## Guide template (mandatory structure)

Every guide follows this structure exactly. Eleven sections, in order,
none skipped. If a section doesn't apply, write `N/A — <reason>` rather
than omitting it.

### 1. When to use this

One paragraph. What problem this service solves; the typical user (e.g.,
"Linux fleet managed by Ansible," "Kubernetes pods needing mTLS," "Cisco
IOS XE devices"); honest acknowledgment of alternatives ("if your fleet
is k8s-only, the ACME guide is probably the better fit").

### 2. Prerequisites

- PyPKI installed and CA initialized → link to `docs/DEPLOYMENT/homelab.md`
- Network ports (inbound and outbound)
- Optional dependencies (HSM, Postgres, webhook receiver)
- Trust anchor situation on the client side — either pre-existing or
  bootstrapped via this guide

### 3. Configuration

- CLI flags relevant to this service, as a table: flag, default, when to
  change
- Config-file entries if applicable
- Which `CertProfile` from `pki_server.py:606` fits this service
- Authentication mode (PAM users, ACME EAB, SCEP OTC, EST mTLS, RA
  approval, etc.)

### 4. Starting the service

- Bare-metal command-line invocation
- `systemd` unit (committed to `docs/HOWTO/units/`)
- `docker-compose` snippet where applicable (drawn from existing compose
  files; don't invent new ones)
- Health-check endpoint and how to confirm the service is up

### 5. Client configuration

At least two reference clients, drawn from the interop matrix in 6.2. For
each:
- Install command (`apt install`, `pip install`, `go install`, etc.)
- Minimum config file or command line
- First enrolment — worked example with real PyPKI URLs
- Renewal command
- Revocation command (where applicable)

### 6. Verification (smoke test)

A copy-pasteable sequence of commands that proves the deployment works
end-to-end. Must be runnable against a fresh PyPKI in under 30 seconds.
Output of each command shown so the reader knows what success looks like.

### 7. Day-2 operations

- Rotating the CA key (link to ceremony docs)
- Revoking issued certs through this service
- Renewing certs near expiry
- Inspecting the audit log for this service's events (which `event_type`
  values to filter on)
- Reading the Prometheus metrics for this service

### 8. Monitoring

- Prometheus metric names specific to this service (e.g.,
  `pypki_acme_orders_total`, `pypki_ocsp_requests_total`)
- Which Grafana dashboard panels show this service (panel IDs from
  `pypki-grafana-dashboard.json`)
- Alert rules worth considering for this service specifically

### 9. Troubleshooting

- The 5 most common failure modes, with how to recognize each in logs and
  metrics
- How to enable verbose logging for this service (`--log-level debug`
  scope)
- For each documented failure mode, link to the regression test in
  `test_pki_server.py` if one exists. If none exists, that's a hint a
  test should be added.

### 10. Security considerations

- Link into the relevant `docs/THREAT_MODEL.md` section
- Residual risks specific to this service
- Operational best practices (e.g., don't expose ACME server to the open
  internet without rate-limit tuning; revoke promptly on key compromise)

### 11. References

- RFCs implemented by this service
- Code modules (`<file>.py`)
- Related guides — other services that interact with this one, topology
  docs that deploy it

## Conventions

- **All commands tested against a fresh checkout.** Cut and paste from
  the doc into a shell on a clean VM; must work without edits.
- **No screenshots without alt text.** Web UI guide will need them;
  others should not.
- **Cross-reference, don't duplicate.** Topology docs (`homelab.md`,
  `k8s-cert-manager.md`) remain the canonical source for installing
  PyPKI. Service guides link in, never copy in.
- **Bash blocks always `bash`-fenced**, never plain. Other shells
  (`fish`, `nu`) get their own fence label and an `# in bash:` comment
  for the bash equivalent if needed.
- **Same template order.** Sections 1–11, in order, none skipped.
- **No marketing language.** Operators want facts and commands.
- **"Last reviewed" header** as for 8.1.

## Sequencing within 8.2

Write guides in this order — most-asked first, easiest interop first:

1. `acme.md` — highest operator interest, easiest to demo, best-tested in 6.2
2. `scep.md`
3. `est.md`
4. `ocsp.md`
5. `cmp.md`
6. `crl.md`
7. `webui-rest.md`
8. `tsa.md`
9. `smime.md`

One guide per session. The template is restrictive on purpose; deviations
get caught in review.

## Per-change checklist (per guide)

- [ ] All 11 template sections present (or explicit `N/A — <reason>`)
- [ ] Every command tested against fresh checkout
- [ ] Cross-references to topology docs verified
- [ ] Prometheus metric names match what the service code emits
- [ ] Grafana panel IDs match `pypki-grafana-dashboard.json`
- [ ] Threat model section linked to actually exists
- [ ] `systemd` unit committed to `docs/HOWTO/units/`
- [ ] "Last reviewed" header set
- [ ] CHANGELOG `### Documentation` entry
- [ ] `docs/HOWTO/README.md` index updated to list this guide
- [ ] Root `README.md` Documentation section links here

## Success criteria

8.2 is "done" when:

1. Every service in the "Services in scope" table has a guide in
   `docs/HOWTO/`.
2. `docs/HOWTO/README.md` is the index and points into every guide.
3. Root `README.md` Documentation section links to `docs/HOWTO/`.
4. Every guide passes its per-change checklist.
5. A new operator, given only `docs/DEPLOYMENT/homelab.md` plus a single
   `docs/HOWTO/<service>.md`, can deploy that service from scratch
   successfully (validate this by walking through with a fresh VM and a
   second pair of eyes).
6. Every guide's "Verification" section runs green against a fresh
   checkout in under 30 seconds.
